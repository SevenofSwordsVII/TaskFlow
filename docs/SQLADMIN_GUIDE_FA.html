۱ معرفی و دلایل انتخاب SQLAdmin

SQLAdmin یک داشبورد مدیریتی مدرن، سبک و با کارایی بالا برای اپلیکیشن‌های مبتنی بر FastAPI و Starlette است که به طور ذاتی با SQLAlchemy (از جمله نسخه 2.x و موتورهای کاملاً غیرهمگام AsyncEngine) هماهنگ می‌باشد.

دلایل انتخاب SQLAdmin برای پلتفرم TaskFlow عبارتند از:

  • پشتیبانی نیتیو از AsyncEngine: بر خلاف پکیج‌های قدیمی که به موتور همگام و بلاک‌کننده (Sync Engine) نیاز داشتند، SQLAdmin نسخه ۰.۳۲ به طور مستقیم با شیء AsyncEngine و نشست‌های AsyncSession کار می‌کند.
  • پرهیز از تکثیر موتور دیتابیس (No Duplicate Engine): دقیقاً از همان شیء app.core.database.engine موجود در پروژه استفاده می‌کند و هیچ کانکشن پول موازی یا مدل تکراری ایجاد نمی‌کند.
  • کنترل دقیق دسترسی سروری (Server-Side AuthenticationBackend): امکان اعمال سیاست‌های سخت‌گیرانه مبنی بر بررسی فیلد is_superuser در هر درخواست با نشست‌های امضاشده.
  • محافظت از مرزهای مستأجران و فیلدهای حساس: قابلیت حذف فیلدهای امنیتی (نظیر هش رمز عبور و هش توکن‌ها) از فرم‌ها و نماها از طریق form_excluded_columns و column_details_exclude_list.

۲ معماری یکپارچه‌سازی با FastAPI و دیتابیس ناهمگام

ادغام SQLAdmin در ساختار ماژولار TaskFlow به صورت یک زیرسیستم مستقل در مسیر backend/app/admin/ پیاده‌سازی شده است:

backend/app/admin/
├── __init__.py       # بسته ادمین
├── auth.py           # بک‌اند احراز هویت نشست‌محور TaskFlowAdminAuth
├── views.py          # تعاریف ۱۳ کلاس ModelView با تنظیمات امنیتی
└── setup.py          # تابع راه‌اندازی و اتصال ادمین به برنامه اصلی (setup_admin)

نحوه اتصال به فست‌ای‌پی‌آی در backend/app/main.py:

from app.admin.setup import setup_admin
from app.core.database import engine

# ثبت و مونت پنل مدیریت در مسیر /admin
admin = setup_admin(app, engine)
عدم تداخل با روت‌های API و کلاینت: پنل مدیریت در مسیر /admin مونت شده و هیچ مداخله‌ای در روت‌های نسخه یک API (/api/v1/*)، روت سلامت (/health) یا روت‌های کلاینت SPA ایجاد نمی‌کند.

۳ احراز هویت و مجوزدهی مدیر کلان (AuthenticationBackend)

کلاس TaskFlowAdminAuth با ارث‌بری از sqladmin.authentication.AuthenticationBackend مدیریت امن نشست را تضمین می‌کند:

تمایز قاطع میان مدیر سازمان و مدیر کلان سیستم

اصل عدم ارتقای خودکار دسترسی: کاربرانی که در یک فضای کاری سازمان نقش OWNER یا ADMIN دارند، به هیچ عنوان مدیر کلان سیستم محسوب نمی‌شوند. ورود به پنل SQLAdmin منحصراً نیازمند فیلد user.is_superuser == True و user.is_active == True در پایگاه داده است.

مراحل لاگین و تأیید نشست:

  1. بررسی نرخ تلاش ورود (Rate Limiting): بررسی آدرس IP کلاینت با محدودیت ۱۰ درخواست در دقیقه برای جلوگیری از حملات Brute-Force.
  2. اعتبارسنجی رمز عبور: اعتبارسنجی پسورد خام در برابر هش ذخیره‌شده با الگوریتم قدرتمند Argon2id.
  3. اعتبارسنجی سوپریوزر: اگر فیلد is_superuser کاربر مقدار False داشته باشد، درخواست بلافاصله رد شده و لاگ هشدار امنیتی ثبت می‌گردد.
  4. امضای نشست: ذخیره شناسه کاربر در سشن با استفاده از کلید رمزنگاری effective_admin_secret_key.
  5. بررسی در هر درخواست (Active Database Re-validation): در تابع authenticate()، شناسه کاربر در هر درخواست ورودی به صفحات ادمین از دیتابیس خوانده می‌شود تا اطمینان حاصل شود حساب کاربر فعال بوده، حذف نشده و از مقام سوپریوزر عزل نگردیده است. در صورت عزل، سشن بلافاصله باطل شده و کاربر به صفحه ورود هدایت می‌گردد.

۴ دستورات CLI ایجاد و ارتقای سوپریوزر

برای جلوگیری از ارتقای پنهانی کاربران در زمان استارت کانتینر یا ایجاد درب‌های پشتی، ابزار خط فرمان backend/app/cli.py توسعه یافته است. این دستورات نیازمند دسترسی به خط فرمان سرور یا محیط داکر هستند:

۱. ایجاد مدیر ارشد جدید (یا ارتقای کاربر موجود به شکل برگشت‌پذیر):

docker compose exec backend python -m app.cli create-superuser \
    --email admin@taskflow.dev \
    --password "StrongSuperPassword123!" \
    --full-name "System Administrator"

۲. ارتقای یک کاربر موجود به سوپریوزر:

docker compose exec backend python -m app.cli promote-user --email user@example.com

۳. عزل دسترسی سوپریوزر:

docker compose exec backend python -m app.cli demote-user --email user@example.com
ویژگی قابلیت تکرارپذیری (Idempotency): اگر کاربر از قبل در دیتابیس وجود داشته باشد، دستور create-superuser رکورد او را به عنوان is_superuser=True و is_active=True به‌روزرسانی کرده و رمز عبور را بدون تداخل در شناسه‌ها آپدیت می‌کند.

۵ پیکربندی متغیرهای محیطی و امنیت کوکی‌ها

تنظیمات امنیتی سشن در backend/app/core/config.py و .env به شرح زیر است:

متغیر محیطی مقدار پیش‌فرض / پیشنهادی کاربرد امنیتی
ADMIN_SECRET_KEY رشته حداقل ۳۲ کاراکتری قوی امضای دیجیتال و رمزنگاری سشن‌های ادمین (در صورت عدم تعریف از SECRET_KEY استفاده می‌شود)

۶ کاتالوگ نماهای مدل (ModelViews) و سیاست‌های CRUD

تمامی ۱۳ مدل عملیاتی سامانه به طور دقیق ثبت شده و مجوزهای آن‌ها متناسب با قوانین کسب‌وکار تنظیم شده است:

موجودیت (Model) کلاس ModelView ایجاد (Create) ویرایش (Edit) حذف (Delete) علت محدودیت عملیاتی
User UserAdmin غیرمجاز مجاز غیرمجاز حذف مستقیم یکپارچگی کلیدهای خارجی را تخریب می‌کند؛ غیرفعال‌سازی از طریق is_active صورت می‌گیرد.
Organization OrganizationAdmin غیرمجاز مجاز غیرمجاز ایجاد سازمان مستلزم انتساب عضو مالک (OWNER) است و از فرم خام ادمین مجاز نیست.
OrganizationMember OrganizationMemberAdmin غیرمجاز مجاز غیرمجاز حذف عضو مستلزم عملیات تراکنشی برداشتن تسک‌ها (Unassign) است.
OrganizationInvitation OrganizationInvitationAdmin غیرمجاز غیرمجاز غیرمجاز نمای فقط-خواندنی جهت بازرسی وضعیت دعوت‌نامه‌ها و تاریخ انقضا.
Project ProjectAdmin غیرمجاز مجاز غیرمجاز ایجاد و حذف باید از طریق سرویس پروژه‌ها برای حفظ ایزولاسیون سازمانی انجام شود.
ProjectMember ProjectMemberAdmin غیرمجاز مجاز مجاز مدیریت انتساب اعضای پروژه با امکان ویرایش نقش و لغو دسترسی.
Board BoardAdmin غیرمجاز مجاز غیرمجاز ایجاد تابلو مستلزم تولید خودکار ستون‌های پیش‌فرض کانبان است.
List ListAdmin غیرمجاز غیرمجاز غیرمجاز ویرایش خام کلیدهای رتبه‌بندی LexoRank یا نسخه‌های OCC نظم ستون‌ها را مخدوش می‌کند.
Task TaskAdmin غیرمجاز مجاز غیرمجاز امکان ویرایش عنوان، توضیحات، اولویت و موعد انجام با حفظ فیلدهای نسخه OCC.
Comment CommentAdmin غیرمجاز غیرمجاز غیرمجاز فقط-خواندنی جهت نظارت بر محتوای گفتگوها بدون امکان تغییر تاریخچه گفتار دیگران.
Notification NotificationAdmin غیرمجاز غیرمجاز غیرمجاز فقط-خواندنی جهت بازرسی اعلان‌های رویدادمحور سیستم.
AuditLog AuditLogAdmin غیرمجاز غیرمجاز غیرمجاز کاملاً تغییرناپذیر (Immutable): هرگونه تغییر لاگ‌های ممیزی ممنوع است.
RefreshTokenSession RefreshTokenSessionAdmin غیرمجاز مجاز غیرمجاز امکان ابطال دستی نشست‌های مشکوک با تنظیم is_revoked = True.

۷ حفاظت از داده‌های حساس و عدم افشای پسوردها

به منظور رعایت اصول OWASP و استانداردهای امنیت سایبری:

  • حذف قطعی هش پسورد: فیلد hashed_password با استفاده از column_details_exclude_list و form_excluded_columns به طور کامل از دید و فرم‌های ویرایش خارج شده است.
  • ممانعت از ویرایش مستقیم هش: هیچ مدیری نمی‌تواند از طریق فرم ادمین رشته هش پسورد را دستکاری کند. تغییر پسورد کاربر منحصراً باید از طریق فرایند امن یا دستور CLI صورت گیرد.
  • حذف توکن‌های خام و هش‌های ریفرش: فیلدهای token_hash در جداول دعوت‌نامه و نشست‌های ریفرش توکن از تمام نماها و فرم‌ها مخفی شده‌اند.

۸ تغییرناپذیری لاگ‌های ممیزی و حفاظت از کانبان

لاگ‌های ممیزی در AuditLogAdmin دارای تنظیمات زیر هستند:

can_create = False
can_edit = False
can_delete = False

این پیکربندی تضمین می‌کند که حتی مدیران کلان نیز نتوانند ردپای اقدامات ممیزی و امنیتی را پاک یا تحریف کنند.

همچنین ستون‌های کانبان (List) به دلیل وابستگی به الگوریتم‌های مرتب‌سازی کسری LexoRank و کنترل هم‌روندی نسخه OCC غیرقابل ویرایش مستقیم در فرم هستند تا از شکسته شدن یکپارچگی پایگاه داده جلوگیری شود.

۹ پیکربندی داکر و دسترسی از پورت‌های ۵۱۷۳ و ۸۰۰۰

پنل مدیریت SQLAdmin به دو روش در دسترس است:

  1. دسترسی مستقیم بک‌اند: http://localhost:8000/admin
  2. دسترسی از طریق پروکسی معکوس Nginx: http://localhost:5173/admin

تنظیمات Nginx در frontend/nginx.conf مسیر /admin را به کانتینر بک‌اند هدایت کرده و هدرهای واقعی درخواست را عبور می‌دهد:

location /admin {
    proxy_pass http://backend:8000/admin;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection 'upgrade';
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

۱۰ آزمون‌های خودکار امنیتی و نتایج تست‌ها

مجموعه تست‌های یکپارچگی در فایل backend/tests/integration/test_sqladmin_security.py پیاده‌سازی شده‌اند:

# اجرای تست‌های SQLAdmin درون کانتینر بک‌اند
docker compose exec backend pytest tests/integration/test_sqladmin_security.py -v

نتایج آزمون تأیید می‌کنند:

  • هدایت کاربران ناشناس به فرم لاگین با کد وضعیت 302.
  • رد قطعی کاربران عادی سیستم.
  • رد قطعی مالکان و مدیران سازمان فاقد مقام سوپریوزر.
  • ورود موفق مدیر ارشد با اعتبارسنجی هش Argon2id.
  • پاکسازی کامل اطلاعات سشن هنگام خروج (Logout).
  • ابطال بلادرنگ سشن در صورت غیرفعال شدن یا عزل مدیر ارشد در دیتابیس.
  • حذف فیلدهای حساس از تمام نماها و عدم امکان دستکاری لاگ‌های ممیزی.
  • صحت کارکرد دستورات CLI ایجاد و ترفیع سوپریوزر.

۱۱ راهنمای رفع اشکال (Troubleshooting)

  • خطای Invalid credentials در زمان لاگین: ایمیل و پسورد را بررسی کنید؛ دقت فرمایید که کاربر باید حتماً فیلد is_superuser=True و is_active=True داشته باشد. با دستور promote-user وضعیت کاربر را بررسی یا ارتقا دهید.
  • خطای 403 FORBIDDEN_ORIGIN در زمان ارسال فرم: بررسی کنید که آدرس دامنه در ALLOWED_ORIGINS ثبت شده باشد یا از همان پورت فراخوانی گردد (میدلور TrustedOriginMiddleware درخواست‌های Same-Origin را معتبر می‌شناسد).
  • مشاهده صفحه 404 در Nginx پورت ۵۱۷۳: اطمینان حاصل کنید که فایل frontend/nginx.conf بلوک location /admin را دارد و کانتینر فرانت‌اند ریستارت شده است.

۱۲ ملاحظات محیط پروداکشن و گام‌های آتی

  • تنظیم متغیرهای امنیتی: قبل از استقرار در محیط پروداکشن، کلیدهای تصادفی قوی برای ADMIN_SECRET_KEY و SECRET_KEY تنظیم کرده و COOKIE_SECURE=true قرار دهید.
  • استفاده از گواهی SSL/TLS: ارتباط با پنل ادمین حتماً باید بر بستر پروتکل HTTPS برقرار شود تا کوکی‌های نشست در معرض استراق سمع قرار نگیرند.
  • آینده‌نگری: در فازهای بعدی می‌توان قابلیت احراز هویت دو مرحله‌ای (2FA / TOTP) را به فرم ورود ادمین اضافه نمود.
